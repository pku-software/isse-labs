### 三、Docker 分層建置、失敗中斷與快取機制

1. **分層建置與快取 (Build Cache)**：
   - Docker 是按照 Dockerfile 的指令順序由上而下一層層構建鏡像的。
   - 如果某一步的指令和相依檔案沒有發生任何改變，Docker 或雲端建置器（ACR）會直接復用上一次構建該層的快取結果。
   - 但只要某一步的內容或指令變更了，從該步驟開始以及後續的所有步驟快取都會失效，必須重新執行。
2. **建置中斷與修復**：
   - 若某一步（例如 `pip install` 安裝失敗）出錯，構建流程會立即中止，後續步驟不會繼續執行。
   - 修復問題後需要重新發起構建。雖然前面未受影響的步驟可能復用快取，但雲端建置（ACR）不保證斷點續跑，因此維護清晰穩定的構建步驟非常重要。

我們在這裡選擇 **WSGI（以 Gunicorn 為例）** 而不是 **ASGI（如 Uvicorn、Hypercorn）**，主要有以下幾個原因：

---

### 1. 框架本身的血統：Flask 原生是基於 WSGI 的同步框架
* **WSGI (Web Server Gateway Interface)**：是 Python 歷史悠久的標準同步協定（PEP 3333）。經典的 Web 框架如 **Flask** 和 **Django** 最初都是完全基於 WSGI 設計的，其請求處理模型是同步阻塞式的（一個請求由一個工作執行緒/行程依序處理到底）。
* **ASGI (Asynchronous Server Gateway Interface)**：是為了解決異步（`async`/`await`）、長連接（WebSocket、SSE、HTTP/2）而誕生的新一代標準，常見於 **FastAPI**、**Starlette** 或 **Quart**。

### 2. 本專案的具體實現方式
檢視我們的 [app.py](file:///Users/apple/.gemini/antigravity-ide/scratch/isse-labs-hw/lab3/2601930020-hsushuoheng/app.py)：
* 我們使用的是標準的 **Flask** 路由函式（一般 `def` 而非 `async def`）。
* 與 DeepSeek API 的通訊使用的是 `requests.post()`，這是一個**同步阻塞式**的 HTTP 函式庫（若在純 ASGI 異步框架中，通常會改用 `httpx` 或 `aiohttp` 來避免阻塞事件迴圈）。
* 服務端只提供常規的 RESTful JSON 請求與靜態資源託管，沒有使用 WebSocket 或全雙工串流長連接。
* 因此，成熟、穩定的 WSGI 伺服器 **Gunicorn** 完全貼合目前程式碼的運行需求。

### 3. 生產環境成熟度與實務考量
* **Gunicorn** 是 Python 社群在容器化部署 Flask 應用時最經典、最穩定的生產級伺服器，設定極度簡潔（例如 `--bind`、`--workers`），且內建完善的行程守護與崩潰重啟機制。
* 如果我們未來將專案重構成 **FastAPI**，或者全面改用 `async def` + `aiohttp` 來高並發處理大模型串流（Streaming Token 輸出），那麼切換成 **ASGI 伺服器（例如 Uvicorn 或 Gunicorn + Uvicorn Worker）** 就會是更理想的選擇。
