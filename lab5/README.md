# Lab5：GitHub Actions 持续集成

> 延续自己的 Lab2 聊天应用，在个人仓库完成自动测试、云端 CI 和本机 runner 实验，再通过课程仓库 PR 提交。

## 如何开始

同步个人 Fork 的课程仓库主分支，在 Codex 中打开 `isse-labs/`，发送：

```text
请完整阅读 lab5/AGENTS.md 和 lab5/README.md，按交互式流程带我完成 Lab5。
```

本次需要新建一个个人 GitHub 仓库，例如 `isse-lab5-chat-ci`，放入自己的 Lab2 应用，用于配置 GitHub Actions 和本机 runner。Agent 会引导你完成创建、克隆和应用复制；实验结束后，将代码、截图和对话轨迹放回课程 Fork 的 `lab5/<学号>-<姓名>/` 提交 PR。

## 作业目标

继续使用自己的 Lab2 聊天应用，完成一次持续集成实践：

- 为聊天记录 CRUD 和一类非法输入编写自动测试，模型调用使用 mock。
- 配置 GitHub Actions，让代码推送后自动运行测试与覆盖率检查，后端覆盖率达到 70%。
- 通过一次功能失败与修复，学会在 Actions 日志中定位问题。
- 适配课程提供的冒烟脚本，检查应用能否启动并提供 HTTP 响应。
- 将同一工作流切换到本机 runner，观察任务在自己的电脑上执行。

### 实验安排

| 阶段 | 要做的事 | 需要看到的结果 |
| --- | --- | --- |
| 准备 | 将自己的 Lab2 应用放入新建的仓库 | 代码与依赖齐全 |
| 测试与 CI | 测试一条聊天记录的 CRUD 和一类非法输入，配置覆盖率检查 | 云端测试通过，覆盖率至少 70% |
| 失败与修复 | 改坏一处功能，推送观察失败，再修复 | 能从日志解释失败原因，修复后通过 |
| 冒烟检查 | 适配课程提供的脚本骨架，加入工作流 | 应用能启动，首页和连通性接口通过 |
| 本机 runner | 注册本机 runner，将同一工作流切换到本机 | 本机接收任务并完成全部检查 |

## Agent 的讲解方式

每次进入下面的 `[AGENT ACTION]`，先面向学生讲解，再开始编码、修改配置或引导操作。讲解结合学生当前应用和上一阶段的结果，说明：

1. **背景**：目前已经完成了什么，接下来涉及什么概念或问题。
2. **目的**：这一步希望解决什么问题，为什么要在这里做。
3. **做法**：准备改哪些文件、执行哪些操作，Agent 和学生分别做什么。
4. **观察**：学生随后应在哪里看到什么结果，怎样判断这一步完成。

用连贯、具体的话解释清楚，新概念第一次出现时配合当前代码或操作举例。讲解之后完成本阶段工作；交给学生操作前，再说明命令含义、执行位置和观察重点，学生反馈后结合真实结果解释再继续。

## 任务 1：自动测试与云端 CI

### 1. 测试两个重点

> [AGENT ACTION]

编写测试前，先讲解：

- **背景与目的**：Lab2 通过网页点击或 curl 验证功能；自动测试把这些请求和预期结果写进代码，让它们能够重复运行。以学生自己的一个聊天接口说明“发送请求”和“断言返回结果”的关系。
- **准备怎么做**：使用 Flask `test_client()` 在测试进程里调用接口，串起创建、查询、修改、删除，再检查一类非法输入。介绍 fixture 如何准备数据，mock 如何把模型调用替换成固定回复，使结果稳定且不消耗真实 API 调用。
- **学生将观察什么**：指出将新增的测试文件、被模拟的模型调用位置和一条具体断言。说明稍后执行 pytest 时，会看到哪些测试通过或哪一条断言失败。

与学生一起阅读实际接口，使用 Flask `test_client()` 编写以下两个重点测试，可放在 `tests/test_chat_api.py`：

| 测试 | 操作与断言 |
| --- | --- |
| 聊天记录 CRUD | 模拟模型返回固定回复；创建记录，查询并核对内容；修改后确认更新；删除后确认消失 |
| 一类非法输入 | 任选空消息或缺少消息字段，检查错误状态和提示，并确认没有新增记录 |

多会话版本先创建测试会话，使用自己现有的接口和响应格式；若通过会话管理记录，说明对应的操作即可。测试记录 ID 从本次响应中取得。

用 mock 替换模型调用函数或客户端，返回固定文本。内存数据在每次测试前重置；JSON 数据使用临时文件。Agent 可协助做少量重构，让数据路径可以配置，例如读取 `LAB5_DATA_DIR` 环境变量，并在加载数据前生效。

添加 `requirements-dev.txt`（pytest、pytest-cov 等）与必要 fixtures，解释一条测试中的请求和断言。测试无需先启动 Flask，也无需访问真实 DeepSeek。

> [STUDENT ACTION]

在仓库根目录安装依赖并运行：

```bash
python -m pip install -r requirements.txt -r requirements-dev.txt
python -m pytest -q
```

看懂两个重点测试检查了什么，将实际结果告诉 Agent。

### 2. 查看覆盖率

> [AGENT ACTION]

测量前，先讲解：

- **背景与目的**：测试通过表示已有断言得到满足，还需要了解运行测试时执行到了哪些后端代码。覆盖率帮助找到尚未涉及的分支，70% 是本次自动检查的通过门槛。
- **准备怎么做**：在原 pytest 命令上增加覆盖率统计、未覆盖行号和门槛参数，逐项解释 `--cov`、`--cov-report=term-missing`、`--cov-fail-under=70` 的作用，结合实际模块确定统计范围。
- **学生将观察什么**：报告中的 `Cover`、`Missing` 与退出结果。若需要补测试，先指出报告对应的实际代码，再解释准备增加哪种请求或断言。

解释覆盖率报告中的 `Cover` 和 `Missing`，提供适合实际项目的命令。单文件后端示例：

```bash
python -m pytest -q --cov=app --cov-report=term-missing --cov-fail-under=70
```

统计范围为自己的后端业务代码；拆成多模块时一并统计。若低于 70%，Agent 根据未覆盖行补充必要测试，学生运行并观察结果。本次只要求理解两个重点测试及覆盖率报告，不逐项验收其他功能的测试，也不要求写测试对应表。

> [STUDENT ACTION]

运行覆盖率命令，确认测试通过且覆盖率至少 70%。

### 3. 添加工作流并推送

> [AGENT ACTION]

修改配置前，先讲解：

- **背景与目的**：测试已经能在本地运行，接下来让 GitHub 在每次代码变更后自动执行同样的检查，减少对手工运行的依赖。
- **准备怎么做**：创建工作流文件，由提交事件触发任务，在云端 runner 中检出本次代码、准备 Python、安装依赖并运行测试。说明云端环境需要重新准备，结合本次配置串起 event、workflow、job、step 和 runner。
- **学生将观察什么**：推送后 Actions 出现新的运行记录，每个 step 对应配置中的一项操作。说明如何核对提交、进入 job、展开测试日志并找到覆盖率。

添加 `.github/workflows/ci.yml`，完成：

1. `push` 到 `main`、向 `main` 发 PR 时触发。
2. 使用 `ubuntu-latest`，检出代码并准备兼容应用的明确 Python 版本。
3. 安装运行与测试依赖。
4. 运行刚验证的测试及 70% 覆盖率检查。

结合配置讲解 `on`、`runs-on`、`uses` 和 `run`。使用当前官方 Action 版本即可。

> [STUDENT ACTION]

提交并推送，在仓库打开 `Actions → 本次运行 → Job → 测试步骤`，找到测试结果和覆盖率。核对运行对应的提交，确认 CI 成功。

> [AGENT STOP]

## 任务 2：观察失败并修复

> [AGENT ACTION]

- **准备怎么做**：选中 CRUD 测试已经覆盖的一处行为，例如删除记录的逻辑。展示这段代码和对应断言，说明将改变哪一行，以及为什么保持原测试预期。
- **学生将观察什么**：推送后应出现失败记录。引导学生按“对应提交、失败步骤、测试名、断言的预期与实际结果”读日志，让学生先说明发现了什么。

> [STUDENT ACTION]

1. 提交并推送这次修改。
2. 在 Actions 中进入失败的测试步骤。
3. 找到失败测试名、断言、预期和实际结果。
4. 将失败截图和运行链接发给 Agent，解释原因。

修复前，先结合学生刚才的观察讲解：

- **背景与目的**：CI 已指出实际行为与预期不一致，现在要用这条失败信息定位应用中的原因。
- **准备怎么做**：把失败断言、实际响应或数据状态、刚才的代码改动对应起来，说明准备恢复或修正哪一处逻辑，以及它为什么能使原测试通过。
- **学生将观察什么**：修复提交会产生一条新的运行记录，同一条测试应恢复通过；对照前后两次提交，确认看到的是新代码的结果。

先将学生发来的失败截图保存到课程个人目录 `screenshots/`，以 `failed` 命名并保留原图扩展名，再根据学生的解释帮助修复应用代码，说明修复与断言的关系。

> [STUDENT ACTION]

重新提交并推送，确认原测试通过。失败与修复是两次独立运行，将两次运行链接发到对话中即可。

## 任务 3：适配冒烟检查骨架

课程提供 [templates/smoke_test.py](templates/smoke_test.py)，已经包含启动、等待就绪、HTTP 请求和退出清理。学生只需适配入口与检查内容。

> [AGENT ACTION]

适配骨架前，先讲解：

- **背景与目的**：test client 已检查接口逻辑，冒烟检查进一步确认应用能作为一个 HTTP 服务启动并响应请求。它会启动临时服务，然后真正访问本机地址。
- **准备怎么做**：复用课程骨架，只适配 Flask 导入入口、首页与连通性接口。带学生读一遍“启动、等待就绪、请求与断言、停止服务”的流程，说明临时端口和临时数据目录的用途。
- **学生将观察什么**：命令执行后先提示服务就绪，再输出两项检查结果，最后停止服务并结束。指出每个输出在骨架中的对应位置。

将课程骨架复制到仓库 `scripts/smoke_test.py`，与学生完成开头配置区：

- `APP_IMPORT`：Flask 入口，通常为 `app:app`；工厂方式可用 `app:create_app()`。
- `HOME_PATH`：首页路径，通常为 `/`。
- `HELLO_PATH` 和 `EXPECTED_HELLO`：连通性接口和预期 JSON，Lab2 默认是 `/api/hello` 与 `{"message": "你好"}`。

持久化版本将数据目录接到 `LAB5_DATA_DIR`：骨架会提供临时目录，应用在初始化时使用它；没有该变量时仍使用原来的数据位置。相关适配由 Agent 协助完成。

先一起阅读骨架的主要流程。它检查首页和连通性接口，静态资源及浏览器交互不作为本次必做项。

> [STUDENT ACTION]

在仓库根目录执行：

```bash
python scripts/smoke_test.py
```

观察服务就绪、两项 HTTP 检查通过、服务已停止。

> [AGENT ACTION]

加入 CI 前，先讲解：

- **背景与目的**：冒烟脚本已经在本地通过，接下来把它也纳入每次提交后的自动检查。

- **学生将观察什么**：新运行的 job 中会多出 `Run smoke test`，其日志应与本地的就绪、检查、停止流程对应，云端成功截图需要保留这些结果。

在 `ci.yml` 的测试步骤之后增加 `Run smoke test`，执行同一命令。

> [STUDENT ACTION]

提交并推送，确认云端测试、覆盖率、冒烟检查都通过，将这次成功运行的截图和链接发给 Agent。截图可分成多张，也可用一张长截图展示关键步骤。

## 任务 4：切换到本机 runner（必做）

> [AGENT ACTION]

- **背景与目的**：此前任务由 GitHub 提供的机器执行，接下来让自己的电脑成为执行任务的机器。代码和检查命令继续使用同一套，变化的是执行位置和环境准备方式。
- **准备怎么做**：在仓库选择系统与 CPU 架构，下载 runner 程序，注册到该仓库，再前台启动。分别解释下载、注册、启动的作用，以及注册 token 的用途和本地使用方式。

### 2. 修改同一份 ci.yml
