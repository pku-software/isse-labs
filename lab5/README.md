## 任务 1：自动测试与云端 CI

### 1. 测试两个重点

> [AGENT ACTION]

**基础讲解：**

> 在 Lab2 中，你通过点击网页或发送 curl 请求检查功能。自动测试把请求、预期结果和判断条件写成程序，以后运行一次命令就能重复检查。测试中的 `assert` 表示一个应该成立的条件，例如创建记录后，返回内容应包含刚才发送的消息。
>
> 我们先做两个重点测试。第一个把一条记录的创建、查询、修改、删除串起来，每次操作后都检查实际内容。第二个发送一类非法输入，检查错误提示，并确认没有新增记录。这样既检查正常操作，也检查输入不合法时的处理。
>
> 聊天接口会调用外部模型，但每次测试都请求真实模型会受到网络、费用和回复变化的影响。这里使用 mock，把模型调用临时换成固定回复，检查应用如何处理这条回复。fixture 负责每次测试开始前准备独立数据，让各次测试从明确状态开始。
>
> Flask 的 `test_client()` 可以在测试进程中向应用发请求，因此这一步不用先启动监听端口的服务。我会添加测试与准备代码，你运行 pytest 后查看哪些测试通过；如果失败，我们就看是哪条断言没有满足。

**结合当前项目补充：** 展示当前 CRUD 接口、准备模拟的模型调用位置，以及一条即将检查响应或数据状态的具体断言。多会话应用说明测试会话如何创建。

与学生一起阅读实际接口，使用 Flask `test_client()` 编写以下两个重点测试，可放在 `tests/test_chat_api.py`：

| 测试 | 操作与断言 |
| --- | --- |
| 聊天记录 CRUD | 模拟模型返回固定回复；创建记录，查询并核对内容；修改后确认更新；删除后确认消失 |

多会话版本先创建测试会话，使用自己现有的接口和响应格式；若通过会话管理记录，说明对应的操作即可。测试记录 ID 从本次响应中取得。

### 2. 查看覆盖率

> [AGENT ACTION]

**基础讲解：**

> 测试通过，表示这些测试中的判断条件得到了满足。接下来还要看看它们执行到了多少后端代码。行覆盖率统计的是测试运行时执行过的可执行语句占被测语句的比例，它能帮助我们找到还没有走到的代码路径。
>
> 覆盖率报告中的 `Cover` 是覆盖比例，`Missing` 列出未执行到的行号。比如测试只发送了合法消息，处理非法消息的代码就可能没有执行。我们可以根据这些行号决定是否补充必要测试。覆盖率高也不意味着所有结果都正确，检查结果是否符合预期还依靠断言。
>
> 这次会在 pytest 命令后加三个参数：`--cov` 指定被测模块，`--cov-report=term-missing` 显示未覆盖行，`--cov-fail-under=70` 设置通过门槛。因此可能出现测试断言全部通过，但覆盖率低于 70%，整个命令仍然失败的情况。
>
> 你先运行这条命令，再把报告发给我。我们一起看覆盖率和未覆盖行，达到门槛就继续；如果还不足，我会结合实际代码补充测试。

**结合当前项目补充：** 确定当前后端的统计范围和准确命令。首次结果出来后，结合真实的 Cover、Missing 和退出状态讲解；需要补充用例时说明要覆盖哪段代码。

解释覆盖率报告中的 `Cover` 和 `Missing`，提供适合实际项目的命令。单文件后端示例：

```bash
python -m pytest -q --cov=app --cov-report=term-missing --cov-fail-under=70
```

统计范围为自己的后端业务代码；拆成多模块时一并统计。若低于 70%，Agent 根据未覆盖行补充必要测试，学生运行并观察结果。本次只要求理解两个重点测试及覆盖率报告，不逐项验收其他功能的测试，也不要求写测试对应表。

> [STUDENT ACTION]

### 3. 添加工作流并推送

> [AGENT ACTION]

**基础讲解：**

> 现在测试可以在本地运行，但每次改代码后仍需要你记得手动执行。GitHub Actions 可以把这条命令放进自动工作流，推送代码或发起 PR 时就执行，让每个提交都有一份检查结果。
>
> 一个工作流由 YAML 文件定义，保存在仓库根目录的 `.github/workflows/`。事件 event 决定何时触发，例如 push；工作流 workflow 组织要做的任务；job 是一组工作，由 runner 上的进程执行；job 中的 step 按顺序完成检出代码、准备 Python、安装依赖和运行测试。
>
> 配置中的 `on` 指定触发事件，`runs-on` 选择执行任务的 runner，`uses` 调用已有 Action，`run` 执行命令。检出代码这一步会取得当前提交的文件。云端任务还需要根据依赖文件安装 Python 包，它不会自动带上你本地虚拟环境中的依赖。
>
> 我会把刚才验证过的测试和覆盖率命令写进工作流。你提交并推送后，到 Actions 打开对应提交的运行，再进入 job，展开测试 step。我们会核对测试结果、覆盖率，以及这份日志对应的是哪一次代码提交。

**结合当前项目补充：** 展示本次 ci.yml 的触发分支、Python 版本、各 step 和测试命令，并给出实际仓库的 Actions 页面入口。

添加 `.github/workflows/ci.yml`，完成：

1. `push` 到 `main`、向 `main` 发 PR 时触发。
2. 使用 `ubuntu-latest`，检出代码并准备兼容应用的明确 Python 版本。
3. 安装运行与测试依赖。
4. 运行刚验证的测试及 70% 覆盖率检查。

结合配置讲解 `on`、`runs-on`、`uses` 和 `run`。使用当前官方 Action 版本即可。
